## PII and privacy boundaries

These are **best-effort controls, not a guarantee that outputs contain no personal data.**

1. **Contact columns are never selected for output.** Phone, email, secondary phone, ID numbers, WhatsApp ids (`customerWaId`, `fromId`, `toId`), business phone ids, external message ids, provider payloads (`payload`, `rawPayload`) and conversation metadata objects are not read by MCP queries. Where a shared product reader selects `phone` (follow-ups, waiting query), the tool drops it or uses the reader only as a SQL subquery so the column never leaves the database.
2. **Lead source is reduced to a channel.** `leadSource` stores `channel:externalId`; only the channel is returned.
3. **Masking of free text.** Lead names and follow-up notes: email-shaped strings and phone shapes of 9+ digits are replaced (`[email hidden]`, `[phone hidden]`). Message text: email/WhatsApp-JID shapes and phone shapes of 7+ digits are replaced; contact-card and location messages return no text. Control characters are stripped; lengths are capped (names 120, notes 280, summaries 1,200, messages 1,000).
4. **Free text can still contain personal information.** A rep or customer can write an address, a full name, an ID number in words, or a number in a format the patterns do not catch. Names are shown by design.
5. **Raw messages only on request.** Message text is returned only by `get_conversation` with `includeMessages=true`, at most 50 messages, each capped, under a stricter hourly rate limit. All other conversation tools return stored summaries only.
6. **Audit never stores text.** `mcp_audit_events.params` keeps ids, numbers, booleans and allow-listed enum values only; every other string (search text, notes, hostile input) is stored as `{len}`. Message text and summaries are never written.
7. **Personal conversations are excluded** from every MCP tool (approved Phase A boundary), matching the product's exclusion of personal threads from AI analysis, auto-responses and notifications.

### `customerName` (decided)

`customerName` is the customer's WhatsApp profile display name (scrubbed of phone/email shapes). `get_conversation` returns it **only for unlinked conversations**, which only ADMIN and GM can open — there it is the only human-readable identification of who is writing. For **linked** conversations the field is absent: the lead's name is already returned, and a second, customer-chosen name is not exposed. No other tool returns it.

## Logging

What SocialCRM's own code logs on the OAuth/MCP path:

- Request ids, tool names, outcomes, error **class and code** (never exception messages — `lib/oauth/server/logSafe.ts`, `lib/mcp/runTool.ts`), sweep counts and duration, and one `user_disconnect` line (user id, grant id, outcome).
- Never: authorization codes, access or refresh tokens, `Authorization` headers, token hashes, PKCE values, `state`, request bodies, message text, search text or contact data.

Request URLs:

- The authorization request is a browser GET, so its query string (`client_id`, `redirect_uri`, `resource`, `scope`, `state`, `code_challenge`) is part of the URL. None of these is a bearer credential: `code_challenge` is a hash, the verifier never travels in a URL, and `state` is a client-generated single-use value. SocialCRM moves the validated request into a signed `HttpOnly` cookie immediately and continues on `/oauth/consent` **with no query string**.
- The authorization **code** appears only in the `Location` header of the consent 303 response and the client's callback URL on the client's own domain; it is never in a request URL to SocialCRM. Access and refresh tokens travel only in POST bodies and `Authorization` headers.
- **Platform request logs cannot be controlled from application code.** Vercel records request paths for its own logs and log drains; this has not been verified in the production dashboard. Treat the authorize query string as potentially visible to anyone with Vercel log access, and restrict that access. The local dev server prints full request lines including query strings — never share a dev log from an OAuth session. Verification step: see [operations.md](./operations.md) → rollout step 6.
