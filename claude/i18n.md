## Architecture

- `lib/i18n/config.ts` — the locale registry (`he`, `en`, `ar`), native names,
  direction, and the region-attribute helpers.
- `lib/i18n/messages/<locale>/<namespace>.ts` — one file per namespace
  (`shell`, `roles`, `settingsNav`, `language`, `common`), composed in
  `<locale>/index.ts`. Hebrew is the **source**; `en`/`ar` namespaces are typed
  `Messages['<namespace>']`, so a missing or extra key is a compile error. Keys
  are `namespace.surface.element[.state]`, one key per whole sentence.
- `lib/i18n/format.ts` — dates, times, relative time, numbers, percent, money.
  Time zone and currency are required arguments (see "Formatting sources").
- `lib/i18n/translate.ts` — `createTranslator(locale)`: `{name}` interpolation,
  CLDR plurals via `Intl.PluralRules` (Arabic: all six categories), numbers via
  `Intl.NumberFormat` (Arabic with Latin digits, matching CRM data).
- `lib/i18n/resolve.ts` — the one precedence rule (pure).
- `lib/i18n/server.ts` — `getUiLocaleState(user)` / `getServerT(user)`: take the
  session user the caller already loaded (no second session read), request-memoised
  by primitives, never `'use cache'`.
- `lib/i18n/I18nProvider.tsx` — `useT()` and `useRegionAttrs()` for client components.
  Outside a provider `useT()` is Hebrew, so un-wrapped renders are unchanged.
- No i18n library: the product needs typed keys, plurals and interpolation, and
  `Intl` already provides the hard parts. Revisit if ICU select/rich text is needed.
- Shared defaults: `Btn as='submit'` with no `lbl` renders `common.save`;
  `toast(kind)` with no message uses `common.toast.*`. The toast container lives
  in the root layout (outside the provider), so `I18nProvider` pushes its
  defaults with `setToastDefaults` and restores Hebrew on unmount.

### Hebrew-leak gate

`__tests__/i18n/surfaces.tsx` registers COMPLETED screens. `leakGate.test.tsx`
renders each in en and ar and fails on Hebrew in any text node or in
`aria-label`/`title`/`placeholder`/`alt`, except exact substrings listed in that
screen's `allowed` entries, each with a reason: `customer-data` (a fixture value
rendered verbatim), `endonym` (a language's own name), `external` (third-party
text). An allowance that is never used fails the gate; every screen must also
render Hebrew in Hebrew, so the gate is never vacuous. No DOM marker exists that
a component could use to exempt itself.

### Native review

`pnpm i18n:export <out.csv>` writes every string (one row per plural form) with
he/en/ar, placeholders and sign-off columns. Sign-off is recorded only by the
owner in `lib/i18n/review.ts`; a locale is offered beyond the pilot only when its
reachable namespaces are signed off. Proposed terminology: `claude/i18n-glossary.md`.

### Resolution precedence

1. `users."uiLocale"` (personal choice)
2. `agencies."uiLocale"` (agency default, admins only)
3. Hebrew

Outside the rollout no query runs and everyone is Hebrew. No browser
`Accept-Language`, no IP/region signal, no automatic switching: every pilot user
is an existing Hebrew user. Detection for new international sign-ups is a later
phase and must never override a stored choice.

### Direction: language islands

`<html lang="he" dir="rtl">` is unchanged — the root layout is static under Cache
Components and cannot read the session, and Hebrew is still the truth for most
of every page. Instead:

- the workspace column (shell + grid) carries `regionAttrs(locale)`;
- `<main>` carries `untranslatedAttrs(locale)` → `lang="he" dir="rtl"` for page
  content not yet translated;
- the settings grid follows the locale, its content cell re-declares Hebrew, and
  the language page declares the locale again.

For Hebrew both helpers return nothing, so a Hebrew user's DOM is byte-identical
to before (asserted in `__tests__/i18n/shell.test.tsx`). Locale is resolved once
on the server and passed as a prop, so SSR and hydration cannot disagree
(hydration asserted for he/en/ar). When a page is translated, wrap its root in
`useRegionAttrs()`.

### Why `<html>` cannot follow the user today (measured, 2026-10-28)

A spike made the root layout read a cookie for `<html lang dir>`. `next build`
failed: *"Route "/admin/support": Next.js encountered uncached or runtime data
during prerendering."* Under Cache Components the root layout is part of every
route's static shell and `<html>` cannot sit inside `<Suspense>`, so it can
never depend on the request (cookies, headers, session). The options:

| Option | SSR-correct `<html>` | Risk |
| --- | --- | --- |
| **Islands (current)** | No — stays `he/rtl`, which is still true for most of every page | None for Hebrew; translated regions are correct |
| Client sync after hydration (`useLayoutEffect` on `<html>`) | No — server HTML still says `he`; flips after JS | Every untranslated portal (dialogs, panels, toasts) would turn LTR for en users: a regression while most UI is Hebrew |
| **Locale root segment**: `app/[uiLocale]/layout.tsx` + `generateStaticParams` (he/en/ar) + `proxy.ts` rewrite from a `ui_locale` cookie | Yes — `<html>` comes from a route param, static per locale | Moves every route under `[uiLocale]`; proxy needs a cookie mirror of the DB preference (stale on another device until next login/save) |

The third is the only SSR-correct design. Its output varies by the locale param
alone (three variants, no user data), so it cannot leak one tenant's state into
another's cache. It becomes worth its cost when the main surfaces are translated
— until then `he/rtl` on `<html>` is the accurate statement. It is a separately
approved phase (see the Phase 2 plan), not part of Phase 1.

### Server locale propagation

1. `DashboardPage` resolves the locale once: `getUiLocaleState(user)` — the same
   request-memoised call the `(app)` layout makes, so page and layout agree.
   Outside the rollout it is Hebrew with no query.
2. Data builders take an optional plain `locale` (default `'he'`):
   `buildTodayBrief(viewer, now, { locale })`, `resolveTodaySnapshot(…, locale)`,
   `modelFromBrief/modelFromSnapshot(…, locale)`, and below them `reasonFor`,
   `greetingFor`, `formatBusinessTime/LongDate`, `waitingReplyCopy({ …, locale })`,
   `recommendReason`, `leadSourceLabel`, `dayLabels`. **Every other caller passes
   nothing and keeps Hebrew**: the MCP tool, the AI agent tool, the mobile API
   (all three project the brief field by field) and the inbox.
3. Server components receive `locale` as a prop and use `translatorFor(locale)`;
   client components use `useT()` from the layout's provider (same value).
4. `generateMetadata` gives the tab title through `getServerT(user)`.

### Logic reads codes, never display text

Each label is a function of a stable code: `ReasonCode` (QualifyingState +
`NEW_INBOUND_TODAY`, `NO_ANSWER_LAST`), `windowState` (WhatsApp window),
`volumeState`/`statusVerdict`, source group, funnel status. Recommendations carry
`reasonCode`; brief items carry `windowState`; mobile tones are resolved on the
server into `MobileTodayModel.tones` (beside the rows, so the row shape is
unchanged). The old Hebrew-text tone functions remain only for hand-built rows
(the frozen a11y suite asserts them) and are marked deprecated.

### Exceptions (data, never translated)

Customer and lead names (and avatar initials), the viewer's first name, meeting
titles, follow-up notes, unknown lead-source strings, AI-generated text. Listed
per screen in `__tests__/i18n/surfaces.tsx`.

## Persistence — migration `20261028120000_ui_locale.cjs`

- `users."uiLocale" text NULL`, `agencies."uiLocale" text NULL`. No default, no
  backfill, no CHECK (the registry grows without a migration; actions validate).
- NULL = no choice → Hebrew. Applying it changes nothing anyone sees.
- `agencies.locale` stays the **billing/invoice** locale and is never read or
  written by i18n.
- Additive, metadata-only, reversible (down drops both columns).
- Code is safe to deploy before the migration while the flag is off (no query
  runs). With the flag on and the migration missing, reads fail closed to Hebrew.

## Security

`actions/uiLocale.ts` takes no ids: user and agency come from the session.
`setAgencyDefaultUiLocale` requires `isAdmin`. Both require the rollout flag and
reject any value outside the registry. DB writes are scoped by `agencyId`.
Not entitlement-gated (reading your own screen spends nothing).
After a save the actions call `refresh()` (re-render the caller's router), not
`revalidatePath`: nothing locale-related is in a shared cache, so nothing needs
invalidating for other tenants.

## Rollout

| Env | Value | Meaning |
| --- | --- | --- |
| `UI_LOCALE_ENABLED` | `1` | master switch (absence = off) |
| `UI_LOCALE_AGENCY_ALLOWLIST` | `103` | agencies in the pilot (`all` = everyone) |

Order: apply the migration → set both env vars in Vercel Production → redeploy.
The order matters: on 2026-10-28 the flag was enabled first, the locale read
failed (`column users.uiLocale does not exist`), the page 404'd, and the menu
still linked to it. The menu now reads the same `enabled` state as the page, so
a failed read hides the link; production migration batch 60 applied the columns.
Kill switch: unset `UI_LOCALE_ENABLED` (stored choices are kept and ignored).

## Adding text to a translated region

1. Add the key to `messages/he/<namespace>.ts` (exact Hebrew), then the same
   key in `en/` and `ar/` (a new namespace also goes in each `index.ts`).
2. Whole sentences with `{params}`; plurals as `{ one, other, … }` objects —
   Arabic must provide every category it uses (the checker enforces it).
3. Dates and money through `lib/i18n/format.ts` with an explicit zone/currency.
4. When a screen is fully translated, register it in `__tests__/i18n/surfaces.tsx`.
5. `pnpm i18n:check` and `pnpm test:i18n` must pass.
